# Complete UI/UX Redesign Brief

I have attached a **design system** and an existing UI design for the MeetUp application.

After reviewing the current design, I am **not satisfied with the overall look and feel**. The current visual direction does not feel distinctive, polished, or mature enough for the product I want to build.

I want you to **redesign the entire UI from scratch**.

This should be treated as a **complete visual and UX redesign**, not a visual refresh or minor iteration.

---

# 1. Core Objective

Create a completely new visual identity and UI direction for **MeetUp** while preserving the existing product functionality and core user flows.

The existing design should be treated primarily as a **functional and feature reference**, not as a visual reference.

Keep:

- Existing features
- Existing functionality
- Existing user flows
- Existing information architecture where appropriate
- Existing MeetUp logo

Completely rethink:

- Visual language
- Layouts
- Typography
- Font
- Color palette
- Spacing
- Component design
- Navigation
- Buttons
- Forms
- Cards
- Tables
- Calendar
- Time-slot selection
- Modals
- Dropdowns
- Tabs
- Status indicators
- Empty states
- Error states
- Interaction patterns
- Overall hierarchy

I want the result to feel like a **new product**, not an improved version of the existing design.

---

# 2. Do Not Preserve the Existing Visual Style

Please do not simply:

- Change a few colors
- Adjust border radius
- Change spacing
- Replace some components
- Add shadows
- Change typography slightly
- Rearrange existing cards

That is not the goal.

Instead, start by asking:

> "If I were designing MeetUp today from a blank Figma canvas, how would I design this product?"

Then create the UI based on that answer.

The existing UI should only tell you:

- What features exist
- What information needs to be displayed
- What actions users need to perform
- How the existing flows work

---

I particularly like the product UI and overall experience of **Apollo.io**.

Use Apollo.io as a strong source of inspiration for the new MeetUp experience.

I like qualities such as:

- Mature SaaS aesthetic
- Strong information hierarchy
- Excellent application shell
- Effective sidebar navigation
- Efficient use of screen space
- High information density
- Clean tables and lists
- Strong typography
- Clear primary actions
- Sophisticated use of neutral colors
- Subtle borders
- Compact controls
- Well-designed filters
- Consistent components
- Professional interaction patterns
- Clear visual hierarchy
- Polished states and feedback

However, **do not copy Apollo.io**.

Do not recreate its:

- Exact layouts
- Colors
- Branding
- Typography
- Icons
- Components
- Screens
- Copy
- Visual assets

Instead, understand the **design principles behind its product experience** and reinterpret those principles for MeetUp.

MeetUp must have its own identity.

---

# 4. Desired Product Personality

I want MeetUp to feel like a **mature, premium B2B SaaS product**.

The personality should be:

- Professional
- Modern
- Premium
- Confident
- Efficient
- Calm
- Intelligent
- Friendly
- Trustworthy
- Minimal

The interface should communicate:

> "This is a serious scheduling product that is extremely easy to use."

It should not feel overly playful or like a consumer mobile application.

It should also not feel cold or corporate.

Find a balance between **professional productivity software and approachable modern SaaS**.

---

# 5. Visual Direction

I want the new visual direction to be **crisp, structured, neutral, and refined**.

The interface should rely heavily on:

- Typography
- Alignment
- Spacing
- Grid
- Proportion
- Borders
- Contrast
- Hierarchy
- Consistency

rather than decorative visual effects.

The UI should look sophisticated because the underlying design decisions are good—not because it contains lots of visual decoration.

Think:

**Less decoration. More design.**

---

# 6. Create a New Color System

Do not simply reuse the current colors.

Develop a completely new color palette for MeetUp.

The palette should include:

### Primary brand color

Create a distinctive primary accent color that works well for:

- Primary buttons
- Links
- Selected states
- Active navigation
- Calendar selection
- Important actions

### Neutral system

Create a strong neutral scale for:

- Application background
- Surface
- Elevated surface
- Borders
- Primary text
- Secondary text
- Muted text
- Disabled states

### Semantic colors

Create carefully controlled colors for:

- Success
- Warning
- Error
- Information

Avoid excessive saturation.

The application should be predominantly neutral, with color used intentionally.

Do not make the entire application colorful.

---

I want you to make an actual design decision about the color system rather than defaulting to the common:

- Purple SaaS
- Blue SaaS
- Purple-to-blue gradient
- Generic Indigo UI

If another color direction is more appropriate for MeetUp, explore it.

The color palette should feel **distinctive but timeless**.

It should work equally well for:

- Internal application
- Public booking pages
- Authentication
- Settings
- Admin interface

---

I want you to reconsider the typography completely.

Do not feel obligated to use the current font from the attached design system.

Select a new typeface that fits the new visual direction.

The font should work exceptionally well for:

---

# 9. Layout Philosophy

The application should have **medium-to-high information density**.

Do not waste large amounts of screen space.

Avoid:

- Huge empty areas
- Giant cards
- Oversized headings
- Excessively tall rows
- Large buttons
- Excessive padding

At the same time, do not make the UI cramped.

The target is:

> **Dense enough to be productive, spacious enough to remain comfortable.**

Think about how a person would use MeetUp every day.

They should be able to quickly scan:

- Meetings
- Guests
- Times
- Meeting types
- Booking status
- Actions

without unnecessary scrolling.

---

# 10. Avoid Excessive Cards

One of the biggest changes I want is to move away from a typical "everything is a card" SaaS design.

Do not put every section into a floating rounded rectangle.

Instead, use:

- Page structure
- Spacing
- Subtle dividers
- Borders
- Background changes
- Lists
- Tables

to organize information.

Use cards only when a card genuinely improves grouping or comprehension.

---

# 11. Application Background

Prefer a subtle neutral background rather than a pure white canvas everywhere.

For example:

- Soft off-white
- Very light neutral gray
- White content surfaces

The exact values should come from the new visual direction.

Avoid strongly tinted backgrounds unless there is a compelling design reason.

---

# 12. Borders and Elevation

Use subtle borders as a major structural tool.

The product should feel mostly **flat and structured**.

Use shadows only when necessary, such as:

- Dropdowns
- Popovers
- Modals
- Floating elements

Do not give every card a shadow.

Avoid heavy outlines.

---

# 13. Border Radius

Use a consistent and restrained radius system.

Avoid:

- Extremely rounded cards
- Excessive pill shapes
- Huge corner radii
- Overly playful shapes

The UI should feel refined and professional.

Use rounded corners where they improve usability, but don't let rounded shapes define the entire visual language.

---

# 14. Navigation

Completely rethink the application navigation.

The navigation should feel similar in quality to a mature SaaS application.

Consider a left sidebar with:

**MeetUp**

Dashboard

Meetings

Meeting Types

Availability

---

Settings

But don't blindly copy this structure.

Explore the best information architecture based on the existing features.

The sidebar should be:

- Compact
- Easy to scan
- Visually quiet
- Clearly grouped
- Consistent

The active item should have a subtle but obvious selected state.

---

# 15. Dashboard

The dashboard should be a **work overview**, not an analytics dashboard.

The most important thing should be upcoming meetings.

Prioritize:

- Today's meetings
- Upcoming meetings
- Quick actions
- Meeting overview

Metrics can exist, but they should remain secondary.

Do not create a dashboard filled with giant statistics.

A user should open MeetUp and immediately understand:

> "What meetings do I have and what do I need to do?"

---
